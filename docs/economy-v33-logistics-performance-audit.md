# Economy v3.3: аудит логистики и производительности

## Область и метод

Аудит текущего кода: `economy`, `economy-routes`, `economy-trade`, `consumer-deliveries`, `household-accounts`, `household-economy`, `autonomous-economy`, `economy-observations`, `economy-history`, `economy-partitions`, `economy-pool`, месячный переход `Simulation` и CLI runner.

Прочитаны уже созданные пользователем `v33-10y-stats.json` и `v33-1710.json`. Агрегация существующего JSON — статический анализ снимка, не новый прогон. Тесты, симуляции, Playwright, бенчмарки и профилировщики не запускались. Экономические формулы, коэффициенты, сортировки участников, маршруты, правила расходования труда и порядок фаз не исправлялись. Изменён только диагностический инструментарий.

Числа производительности ниже принадлежат пользовательскому прогону, не измерениям агента. В файле v3.3 записаны 1 921,10 с, медиана месяца 15,574 с, размер GameState 95 550 006 байт, пик RSS 1 876 791 296 байт. Записанное время внешних отчётов — 29,90 с, около 1,56% общего времени; это не включает аналитические вычисления внутри месячного перехода. Сравнение с указанными пользователем 558 с v3.2 даёт около 3,44 раза, но распределение затрат по фазам пока неизвестно.

Нельзя объяснять все 567 тысяч недостаточным новым производством.

## Подтверждённые дорогие участки

Обозначения: `C` — грузы, `H` — домохозяйства, `N` — предприятия, `M` — рынки, `E` — рёбра, `L≤12` — путь, `G` — товары, `B` — строки покупателей, `Sg` — рынки-поставщики товара.

| Файл / функция | Подтверждённый механизм | Верхняя оценка / значение |
|---|---|---|
| `economy-routes.validate` | Внутри цикла cargo для продавца-домохозяйства вызывается `householdEconomy.rows.some`. Для производственного владельца-домохозяйства есть второй аналогичный поиск. | `O(C·H + C·L)`. В снимке 31 048 грузов от домашних продавцов; только успешный поиск их продавцов требует **58 879 632** проверок предиката за один полный вызов на этом снимке. Число получено по позициям продавцов в сохранённом массиве, без запуска валидатора. |
| `economy-trade.validate` | Аналогичный линейный поиск продавца в каждом соседнем flow. | `O(F·H)` для таких flows. |
| `Simulation.#advanceDay`, `economy.prepareEconomyMonth`, `prepareValidatedMonth`, `economy-trade.coordinate` | Полная проверка открывающего состояния, подготовленного результата, торгового результата, результата после координатора и после развития. | Для обычного последовательного торгового месяца — пять проходов route validation. Каждый нужен текущей архитектуре; стоимость нельзя считать один раз. Состав грузов меняется между проходами. |
| `economy-routes.opportunities` | Кэшированный BFS не устраняет проход по всем поставщикам каждой заявки; для каждой пары снова просматривается путь, оцениваются работники и проводится бинарный подбор количества. | `O(M·(M+E) + Σ B_g·Sg·(L+log Q))`, с ограничением reachable BFS. Это реальная дополнительная работа v3.3 относительно простого сравнения котировок. |
| `economy-routes.coordinate / candidates` | Для каждого покупателя посещаются все группы источников товара, проверяются живые предложения, затем сортируются доступные котировки. Даже покупатель с нулевым остатком может пройти этот поиск, прежде чем сделка пропускается. | `O(Σ B_g·Sg·log Sg)` плюс просмотр предложений и BFS. Генератор ограничивает память котировками одного покупателя, но не устраняет перебор пар. В последнем месяце записано 6 265 268 отказов по маршруту — это попытки пар, не миллионы уникальных покупателей. |
| `economy-routes.coordinate / paths` | BFS кэшируется по источнику; хранится полный массив пути к каждой достигнутой вершине. | До `O(M²·L)` ссылок в локальном кэше, в зависимости от достижимости. Он освобождается после вызова и не растёт между месяцами. |
| `economy-routes.coordinate` | Копирование и сортировка всех oldCargo по ID, затем попытка перевозки каждого. | `O(C log C + C)`; последующая проверка пути `O(C·L)`. Много мелких грузов дороже одного большого равного объёма. |
| `economy.validate` | Для каждого товара повторно просматриваются физические запасы, cargo, inUse и состояния потребителей. | `O(G·(C+H+N))` с дополнительными маленькими линейными поисками товара. |
| `economy.prepareValidatedMonth` | Полный structuredClone экономического состояния, канонизация и несколько новых индексов и промежуточных описаний incoming. | `O(размер состояния)` на копирование; растёт с cargo. Временные массивы и объекты увеличивают давление на GC. |
| `economy-history.append / analytics`, `economy-observations.summarize`, `autonomous-economy.report` | История каждый месяц вычисляет наблюдения; затем runner повторно делает отчёт. summarize рассчитывает вложенную новую диагностику даже когда история сохраняет только старые числовые поля. | Повторные `O(C+H+N+G·H)` проходы и построение индексов. Внешние 29,9 с не объясняют всё замедление, внутренние расходы ещё не измерены. |
| `autonomous-economy.develop` | Для каждой устойчивой shortage и рецепта проверяется наличие оборудования через `enterprises.some`. | До `O(shortages·recipes·N)`, зависит от числа кандидатов на вход. |

Наличие этих обходов доказано кодом. Их процент в 1 921 с, стоимость GC и максимальный одновременно живой кэш **не измерены**. Основной кандидат первой оптимизации — индексы валидаторов, но даже этот вывод не заменяет профиль.

`routing.planning` имеет ещё линейный поиск всех участников для каждого incoming descriptor; в обычной последовательной подготовке поле удаляется перед закрывающей валидацией. Этот условный участок нельзя выдавать за подтверждённый горячий путь каждого месяца.

## Логистика: точный порядок и ограничения

1. Открывающий `opportunities` использует текущие деньги, запасы и ожидаемые грузы. Сначала условно распределяет местное предложение, затем выбирает **один** внешний источник с минимальной доставленной стоимостью. Товар и транспорт при этом не резервируются.
2. `autonomy.begin` переносит сигналы между рынками и распространяет требования по рецептам. Открывающий прогноз не гарантирует выпуск, наличность продавца или свободный транспорт после производственных фаз.
3. Производство использует открывающие inputs. Сельское хозяйство, потребление, локальные покупки и установка оборудования происходят до глобальной маршрутизации. Перевозчикам достаётся оставшийся труд, не весь показатель участия населения.
4. Координатор замораживает экспортируемые остатки **до** продвижения старых грузов. Старые грузы обслуживаются по ID раньше новых, максимум по одному ребру.
5. Покупатели и предложения группируются по товару. BFS сохраняет только кратчайший допустимый путь с детерминированным порядком соседей, максимум 12 рёбер и единой accountingUnit. Загруженность ребра не участвует в выборе пути; более длинный обход не ищется.
6. Котировки сортируются по цене исходного товара плюс перевозка **заявленного** количества по всем рёбрам, затем по ID источника. Реально купленное количество может оказаться меньше. При неделимой цене труда округление означает, что порядок котировок для большого запроса не обязательно оптимален для маленького фактического лота. Это алгоритмическое ограничение, не доказанная потеря денег.
7. Для новой поставки проверяется остаточная ёмкость первого ребра; на будущих рёбрах используется полная месячная ёмкость и текущий остаток труда. Ни будущее место в очереди, ни будущие работники не резервируются. Будущая конкуренция может остановить уже оплаченный груз.
8. Покупка дебетует товар и весь freight, кредитует продавца, списывает его физический склад. Первая перевозка оплачивается сразу. Остальной freight остаётся `escrowMinor`; стоимость товара увеличивается только на реально оплаченные этапы. При каждой следующей перевозке escrow уменьшается на fee и столько же входит в book value и деньги перевозчика.

### Что может удерживать грузы

`transport` принимает груз целиком: нужны `ceil(quantity/unitsPerWorker)` работников и ёмкость для всех единиц. При отказе нет частичного продвижения. У грузов нет срока жизни, отмены с возвратом, нового маршрута или уменьшения лота. Если остаток труда на требуемом этапе всегда меньше требуемого, груз способен не продвигаться неопределённо долго. Аналогично работает длительная конкуренция за ребро. Это возможность кода, а не установленный возраст конкретных 116 тысяч грузов.

Приоритет старых ID помогает старым **выполнимым** грузам, но не гарантирует прохождение слишком крупного. Его отказ не резервирует остаток ребра: меньшие следующие грузы могут пройти и снова оставить ему недостаточно места. Переход через одно ребро использует одну провинцию-перевозчика, выбранную данными ребра; это также часть модели.

На снимке только 88 грузов с 107 722 единицами превышают **сохранённый конечный** остаток труда своего следующего перевозчика. Это не доказывает, что труд не ограничивал месяц: он уже расходован, а ёмкость `used` в сохранение не попадает. По конечному снимку нельзя восстановить отказ в момент конкретной попытки.

### Продовольственный горизонт и заявки в пути

Одежда: `consumer-deliveries.demands` вычитает собственные доставленные остатки и cargo того же сектора из неудовлетворённой физической потребности. Новая заявка при существующем грузе допустима, если он не покрывает всю потребность. Излишек мира в другом секторе/у другом владельца не становится доступным потребителю автоматически.

Продовольствие: перед **каждым предложением** пересчитывается `remaining = foodNeed·hops − holding − naturalCoverage`. `holding` увеличивается после новой покупки, поэтому одинаковый горизонт не покупается повторно вслепую. Но более длинный следующий маршрут увеличивает целевой запас и может снова открыть уже исчерпанную короткую заявку. Грузы в пути вычитаются без учёта их ожидаемой даты доставки; старый остановленный груз может удерживать потребность от новых заказов.

Есть подтверждённое несоответствие горизонтов: `opportunities` прогнозирует текущую месячную потребность через `consumer-deliveries.opening`, а фактическая продовольственная закупка может нацеливаться на `hops` месяцев. Следовательно, полный фактический внешний заказ не обязательно заранее представлен в сигнале производителю. Кроме того, секторный `foodNeed` координатора не вычитает все уже съеденные местные покупки — он также работает как запас будущей поставки. Это требует отдельного решения о политике запаса; молча менять формулу нельзя.

Для одежды входящий оплаченный груз учитывается в `affordableDemand`, но остаётся в `unmetNeed` до использования. Поэтому физически неудовлетворённый платёжеспособный спрос в отчёте не всегда означает ещё не выполненный заказ на рынке.

## Жизненный цикл и балансы

| Категория | Получение и последующее использование |
|---|---|
| Потребительское food | Доставка в прежний `trade.householdStocks`, секторная принадлежность как подмножество. Следующая фаза потребления списывает товар и `consumedImports`; натуральная еда отдельно списывается с мастерской. |
| Одежда и другие durable consumer goods | Доставка в `consumerStocks`; в следующем месяце физическое использование переносит quantity/book value в `inUse`, затем существующий износ. |
| Промышленные inputs | Доставка в единственный inventory предприятия. Производство уже произошло, значит закупка доступна для следующего производственного месяца. |
| Оборудование | Доставка в inventory. `autonomy.finish` был раньше доставки; в следующем месяце установка требует pendingCapacity, оборудование, деньги сверх резерва и реальный труд. Получение не означает автоматическую установку. |
| Сельские inputs | Груз `purpose:production` поступает в inventory мастерской и ledger.bought; используется последующим месячным циклом. |

Списанный склад, лимит предложения и живой quantity исключают повторную продажу одной единицы в исследованном пути. Старый доставленный cargo удаляется из нового массива; соседний сразу доставленный груз в cargo не добавляется. Новый входящий товар не включается повторно в открывающие экспортные предложения этого месяца.

Продовольственный торговый баланс учитывает соседний food через flows, многошаговое завершение через deliveredFood. Для соседней доставки deliveredFood специально уменьшается на q, чтобы не посчитать тот же food дважды. Финансовое закрытие включает остаток escrow, физическое — склады, consumerStocks, мастерские, cargo и отдельно inUse/installed capital. BigInt используется для произведений, стоимости и проверок; месячный результат устанавливается после валидации.

В этих просмотренных ветках **не установлено** создание товара/денег, двойное получение или двойное потребление. Это статический вывод; доказательство всех траекторий требует тестов. Серьёзную подтверждённую ошибку физического/денежного сохранения аудит не обнаружил. Изменять экономический баланс на основании этого аудита не следует.

## Добавленная диагностика

Явный флаг `--profile-economy`, по умолчанию false. Требует `--workers 0` и `--stats`; сочетание с прежним `--benchmark` отвергается, чтобы не смешивать обёртки и области покрытия. Многопоточное профилирование внутренних фаз сейчас **не реализовано**, ограничения сообщаются явно.

Новый `shared/economy-diagnostics.cjs` хранит process-local session и небольшую запись возраста/остановок на каждый активный ID. В GameState/cargo новых полей нет. Завершённые ID удаляются, после stop очищается весь индекс. В JSON статистики добавляется необязательный `economyDiagnostics:{version:1,coverage:'sequential-only',months:[...]}`. История и сохранение симуляции не расширяются. Экспортируются только агрегаты за месяц, без списка отдельных грузов.

При выключении нет диагностических обходов cargo, гистограмм, часов или экспортных обёрток. Остаются проверки наличия trace в местах инструментирования; практически нулевую стоимость этих ветвей нельзя утверждать без пользовательского сравнения.

### Время и числа объектов

- Последовательные внутренние интервалы core: `statePreparation`, `autonomousPlanning`, `production`, `householdsAgriculture`, `marketOrders`, `localDeals`, `pricesAndPayouts`, `investmentFinish`, `closingStatistics`, `preparedValidation`.
- Routing: `routingPreparation`, `cargoAdvanceDelivery`, `externalMarketOrders`, `tradeCandidateSearch`, `successfulShipmentCreation`, `logisticsAggregation`.
- Детализация BFS: `forecastBfs`, `tradeBfs`; полный прогноз `forecastOpportunities`; общая торговая фаза `tradeSearchAndShipmentsInclusive`.
- Обёртки `inclusive.*`: подготовка экономики, публичная валидация, validate торговли/маршрутов, координатор торговли, population, settlements, develop, history.append, observations.summarize. Внешний отчёт — `runnerReportInclusive`.
- Каждая запись содержит calls, totalMs и objects — число строк на границе фазы, а не число каждого внутреннего чтения свойства. `marketOrders` включает потребление домохозяйств и построение/сортировку заявок; `statePreparation` включает прогноз и клонирование. Их разделение описано, а не скрыто.

**Вложенные времена нельзя суммировать.** Например, `tradeBfs` входит в `tradeCandidateSearch`, а оба входят в `tradeSearchAndShipmentsInclusive`; `inclusive.economy.prepareEconomyMonth` включает начальную проверку и все core-фазы. Начальная проверка использует лексическую функцию и не попадает в экспортную обёртку economy.validate: её вложенная routes.validate измеряется отдельно. `successfulShipmentCreation` покрывает только успешные попытки, включая первую перевозку/соседнюю доставку. Время неуспешных попыток остаётся в общей торговой фазе. Первоначальная сортировка покупателей тоже включена в общий интервал, а не per-buyer search.

### Логистические показатели

- opening, created/createdQuantity, delivered/deliveredQuantity, active/quantity, advancedOld, stalled/stalledQuantity;
- причины остановки старых грузов: labor и capacity. Они могут пересекаться; это не взаимоисключающее разбиение;
- cancelled=0: в текущем движке нет отмен. Необъяснимое исчезновение наблюдавшегося ID отмечается как unobservedRemovals, а не выдуманная отмена;
- известный возраст: корзины 1, 2–3, 4–6, 7–12, 13–24, 25–60, 61+ месяцев, количества записей и единиц; такой же разрез по товару;
- неизвестный истинный возраст загруженных грузов и отдельный observedAgeLowerBound; он не выдаётся за дату отправления;
- mean/maxServiceMonths для завершённых поставок известного возраста; соседняя занимает 1 обслуживающий месяц, два ребра без ожидания — 2. mean/maxElapsedMonths считает прошедшие месячные границы: соседняя 0, два ребра 1;
- завершения неизвестного возраста исключены из средних и имеют отдельный unknownCompleted. Средние описывают завершённые, не ещё ожидающие поставки;
- maxConsecutiveStalls с начала наблюдения, активные по длине пути и index, escrowMinor, remainingQuantityEdges — объём оставшейся перевозочной работы;
- repeatRequests — положительные новые запросы при положительном pending того же владельца/товара. PendingQuantity суммируется по событиям и может повторять один остаток. Это индикатор пересечения, **не доказанное двойное списание**; foodRetargets отдельно считает увеличение цели и повторное открытие исчерпанной заявки;
- forecast/trade RouteRequests, RouteCacheHits, BfsBuilds, CacheEntries; число посещённых групп поставщиков, допустимых кандидатов, попыток предложений и строк покупателей;
- routeValidationCalls и routeValidationCargoRows для связи времени валидатора с ростом очереди.

Объёмы remainingQuantityEdges и другие суммы диагностические, вычисляются Number и не участвуют в правилах. Для экстремальных состояний с произведениями выше MAX_SAFE_INTEGER их нельзя использовать как точный бухгалтерский регистр. Денежная и физическая бухгалтерия остаётся прежней.

## Совместимость Workers и план оптимизации

Разделение подготовки по рынкам сохраняется. Открывающий общий прогноз строится в координаторе, incoming descriptors проецируются к владельцам; внешняя торговля выполняется после merge. Это подходящая граница для независимых производственных фаз, но глобальная логистика остаётся последовательной.

`Simulation.stepAsync` вызывает reset после торгового/домашнего результата: потоки завершаются, следующий месяц создаёт их заново и передаёт projections. Поэтому существующий pool для такой кампании не фактически постоянный между месяцами; structured-clone сообщений, startup и merge добавляют стоимость. Нельзя ожидать ускорения всего месяца от числа workers: координатор и полные проверки не параллельны. Диагностическая singleton session намеренно не передаётся в worker realm; режим с workers>0 запрещён CLI, чтобы не показывать неполный профиль как полный.

Рекомендуемая последовательность следующего этапа:

1. Пользовательские короткие измерения фаз и проверка equivalence профилирование off/on. Отдельно ранний мир и продолжение 1710 с большим cargo.
2. После разрешения оптимизации: индексы household seller/owner membership в валидаторах, индексы товаров и actors с прежними проверками. Не убирать проверки балансов. Сравнить полный результат и порядок ошибок для некорректных состояний.
3. По измерениям: исключить поиск источников для уже исчерпанных заявок, индексы компоненты/accountingUnit и живых источников. Осторожно: food-цель меняется с длиной маршрута, простой `remaining===0` early exit может изменить экономику.
4. Сохранить BFS-соседей/tie-break, перейти с полных путей ко всем вершинам на parent+distance и реконструировать выбранные пути. Оценить ограниченный долговечный кэш с инвалидированием по графу/валютам/правилам. До этого измерить число cache entries и память.
5. Разделить дешёвые числовые observations для history и подробный отчёт; переиспользовать локальные индексы в пределах неизменного этапа. Не кешировать живые деньги, quantity и труд без инвалидирования.
6. Исследовать копирование/канонизацию и повторные проверки, сохраняя validation-before-commit и failure atomicity. Замена полной копии требует отдельного дизайна транзакции и эталонных тестов.
7. Отдельное согласование экономических решений: единый food-горизонт для прогноза и заявки, частичные перевозки, ограничения отправки по очереди, rerouting/отмена и управление запасом. Это не просто ускорение; изменит траекторию и стоимость доставки.
8. Для v4: постоянные worker threads, компактные сообщения, детерминированное распределение глобальных транспортных конфликтов. GPU и крупная многопоточная переработка в этом аудите не реализованы.

## Пользовательская проверка

Ни одна команда ниже агентом не запускалась. Сначала новая диагностическая регрессия, включая полное совпадение состояния и продолжение save/load:

```powershell
npx playwright test tests/economy-diagnostics.spec.cjs tests/economy-v33.spec.cjs --config playwright.ci.config.cjs
```

Короткий контроль нового старта; выбрать свежие имена, runner не перезаписывает существующие файлы:

```powershell
node scripts/world-economy-demo.cjs --seed 1700 --autonomous --workers 0 --months 12 --summary-every 12 --profile-economy --stats ./v33-profile-start-1y.json
```

Нагруженный контроль из **существующего** сохранения без изменения настроек экономики:

```powershell
node scripts/world-economy-demo.cjs --load ./v33-1710.json --workers 0 --months 12 --summary-every 12 --profile-economy --stats ./v33-profile-resume-1y.json
```

При необходимости полный контроль с seed 1700:

```powershell
node scripts/world-economy-demo.cjs --seed 1700 --autonomous --workers 0 --months 120 --summary-every 12 --profile-economy --stats ./v33-profile-10y.json --save ./v33-profile-1710.json
```

Для оценки собственной накладной стоимости инструмента повторить те же исходные условия без `--profile-economy`, с другими именами stats/save. Длительности profiled запуска включают время диагностических счётчиков; их нельзя выдавать за скорость обычного режима.

Интерпретация:

1. Сопоставить rows cargo и inclusive.routes.validate во времени, затем сравнить с поиском кандидатов и forecast. Это установит реальный вклад двух основных подозреваемых.
2. Проверить баланс числа `active_end = opening + created − delivered` при cancelled=0; отдельно изменение quantity и monthly flow. Сравнивать trade.quantity осторожно: это единицы-рёбра всех перевозок, не количество отправленных товаров.
3. Для мира из нового старта проверить хвост 13–24/25–60/61+ и длительность доставки против длины пути. Рост хвоста, stalled и remainingQuantityEdges отделяет очередь от нормального transit stock. Старые загруженные грузы имеют только нижнюю границу возраста.
4. Применять отношение transit quantity к среднему месячному потоку только для устойчивого периода, одного товара и согласованной единицы: средняя по отправлениям длительность не равна средневзвешенной по единицам. Текущий инструмент не выдаёт взвешенную длительность; простой снимок/последний месяц не доказывает закон очереди.
5. Сопоставить одежду по владению: inTransit/paid coverage, arrivals, deliveredUsed, unmet, доступную новую покупку, географию и секторные деньги. Не считать оплаченный груз новым необслуженным спросом.
6. RepeatRequests и foodRetargets требуют анализа горизонта. Высокий cache-hit не исключает дорогой перебор пар; смотреть также SupplierGroupsVisited и tradeCandidates.
